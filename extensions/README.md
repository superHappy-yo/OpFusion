# extensions — 算子与设备扩展

状态：扩展机制的工程规格。当前没有插件加载器、算子实现或设备适配代码。本文约定未来新增内容的位置与验收标准，不代表复制目录后已能运行。

## 目标与边界

在既有公共契约能够表达新能力时，新增算子、设备型号、编译适配器或区域实现，只增加对应插件目录；不修改 frontend、fusion、planner、codegen、runtime 等核心流程，不维护一份每次都要改的中央注册列表。

这依赖稳定接口、组合、显式发现与能力查询。面向对象可以实现这些接口，但深继承树不能保证扩展性。推荐以小型 C++ 端口接口和必要的抽象类描述行为，以不可变记录描述语义与能力；核心消费接口和能力，不根据算子名或设备型号不断添加条件分支。

## 扩展目录

未来插件使用以下四类约定根。每个 `<plugin_id>` 目录是一个独立修改范围，包含自己的 `plugin.toml`、实现、测试和说明；没有真实任务时不预生成空实现。

```text
extensions/
  operators/<plugin_id>/         算子语义及相关贡献
  devices/<plugin_id>/           设备描述、探测或运行适配
  compilers/<plugin_id>/         编译工具链适配
  implementations/<plugin_id>/   已有算子的特定实现、lowering 或库绑定
```

类别决定主要所有权，不要求一个插件只能贡献一种接口。新增算子可以在同一插件内同时提供语义、前端绑定、参考实现和目标 lowering，避免要求修改多个已有模块。共享能力通过声明的 provider ID 与版本复用，不能导入兄弟插件的内部代码。

完整字段、端口和冲突规则以 [扩展契约](../modules/contracts/extensions.md) 为准；任务使用 [扩展任务模板](../docs/ai/extension-task.md)。

## 新增一个算子需要提供什么

| 内容 | 用途 |
|---|---|
| 版本化语义标识、端口和属性 | 明确这个算子需要计算什么，避免只有名称没有语义 |
| shape/dtype 校验与推导 | 使前端和图验证器能检查合法输入输出 |
| 索引、广播、归约及副作用等特征 | 为通用融合规则和特征提取提供依据；未知特征不能当作任意可融合 |
| 外部格式绑定 | 将 ONNX domain/opset 等来源映射到规范语义；首版优先 ONNX |
| 参考执行或可验证分解 | 提供正确性比较依据；参考实现不等于高性能实现 |
| 可执行方案 | 提供目标 lowering、库实现或能够复用现有算子的合法分解，至少覆盖声称支持的目标 |
| 测试与支持矩阵 | 覆盖属性、shape、dtype、数值边界及明确不支持的组合 |

若新算子能够分解为已有算子，并满足数值政策，可以复用已有后端，不要求每个设备再写一份实现。若算子保持不透明，必须有明确支持它的实现；未知成本返回未知，不能填零。导入可识别与目标可执行分别报告。

例如新增 Sigmoid，应在一个算子插件中登记语义、输入输出推导、ONNX 绑定和参考/目标方案。frontend 从注入的算子目录查找绑定；fusion 查询特征；codegen 查询可用方案。各核心模块不新增 `if op == "Sigmoid"`。这里描述的是未来验收用例，当前没有该插件。

## 新增设备的两种情况

| 情况 | 需要新增的内容 | 可以复用什么 |
|---|---|---|
| 已支持架构中的新型号或新实例 | 描述、识别条件、资源/能力信息、已有 provider 引用及适用版本；新实例信息由配置或探测产生 | 现有编译器、加载/执行适配器、算子实现 |
| 新的执行架构或 SDK | 描述之外，还需在本插件提供适配器贡献，或通过明确的集成任务增加独立编译插件 | 只有明确兼容的契约与能力可以复用 |

添加峰值算力、带宽和容量不能自动生成缺失的指令降低、内核加载或执行支持。设备型号被识别后，还要检查具体区域、shape、dtype、布局、数值模式和软件版本。新设备未测的代价不能冒充实测值。

例如某 GPU 新型号已经被现有驱动和编译器支持，可以只新增设备插件的描述与匹配信息，并完成适配验证；全新 NPU 若缺少编译和运行适配，就不能只写配置声明支持。设备实例 ID、设备型号 ID、编译器 ID 与执行 provider ID 分别管理。

## 如何被系统识别

1. apps 在显式启动/装配阶段枚举四类约定根下的插件清单；只读元数据，不靠导入副作用向全局字典注册。
2. 验证插件 API、贡献类型、唯一标识、版本依赖和引用完整性。重名或冲突不能按目录顺序静默覆盖。
3. 按请求加载所需 provider，执行单独的支持查询或设备探测；单纯发现插件不得初始化全部硬件或执行测量。
4. 将解析结果构造成当前应用实例的不可变目录快照，通过 contracts 端口注入消费者。
5. 编译、数值验证和测量分别产生记录；正式计划只使用满足执行契约的候选。

新增插件在下一次显式发现/重建快照时生效，不原地更改正在使用的计划。未实现热插拔、远程下载安装或任意第三方插件市场。

## 未来必须证明的性质

- 新增插件目录后能够发现其声明；删除该目录后该贡献消失，无需编辑中央列表。
- 重复 ID、不兼容 API、缺失依赖、前端绑定冲突能得到确定诊断。
- 导入扩展不启动设备、不执行网络请求、不测量性能，不修改进程级全局注册表。
- 已支持的扩展只修改授权插件目录；公共契约确有缺口时另提具体变更，不能修改提示词自行扩权。
- 算子比较参考语义，设备进行真实目标适配验证；未具备硬件条件时明确未验证。
- 核心消费者通过契约测试证明可接入新 provider，而非新增特例分支后才通过。

提示词只能规定行为。目录写入限制和自动范围检查仍需按 [强制机制规格](../docs/ai/enforcement.md) 实现与验证。
