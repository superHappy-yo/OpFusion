# 公共契约变更流程与提示词

公共契约由 `modules/contracts/` 集中维护。普通模块任务只读这些定义；发现需求时在自己的 `proposals/` 中提出建议，不能在本模块另造同名协议或类型。

契约包括数据对象、字段和单位、版本、状态、错误、数值政策、生命周期、输出就绪、资源作用域，以及生产者和消费者各自的责任。改变这些含义属于契约变更，即使字段名未变。

## 1. 模块 proposal 模板

在 `modules/<module>/proposals/<short-name>.md` 中记录以下内容。proposal 是待处理建议，不自动改变当前契约或扩大写入权限。

```text
标题：<契约变化>
状态：Proposed
提出模块：<module>
当前契约：<文件/对象/版本>
触发问题：<可复现输入或具体任务>
当前行为：<旧字段及语义>
建议行为：<新字段、单位、约束和错误处理>
影响方：<生产者、消费者、验证和装配入口>
兼容方案：<保持兼容/新版本/迁移及回退>
验证方案：<契约样例、失败样例和组合测试>
所需修改范围：<逐模块列出路径>
尚未决定：<仅列影响正确性的事项>
```

例如将时延从 μs 改成 ns、改变工作区是否包含输出缓冲、让未验证候选进入可执行清单，都不是某个预测器的内部重构。

## 2. 契约维护任务模板

```text
任务：落实 <proposal> 中已获授权的公共契约变化。
角色：contracts 维护任务。
允许修改：<modules/contracts/ 下具体规格、样例和契约测试路径>
只读：<受影响模块公开接口及相关架构决定>

先核实用户授权范围和现有契约，不根据 proposal 自行扩大任务。
明确新旧语义、版本、单位、生命周期、失败状态及兼容/回退方式。
同步更新授权范围内的契约示例及验收定义。
列出下游适配任务，但不要直接修改其他模块。
所有治理提示词、scopes.json 和根配置仍默认只读。
完成后报告契约差异、受影响方和可检查的兼容性结论。
```

## 3. 集成顺序

1. 集成任务检查现有接口是否已经足够，避免不必要的公共字段扩张。
2. 在既有授权范围内确定新旧行为与兼容策略；没有授权的范围变化应提出具体需求。
3. 契约维护任务更新规格和验证样例。
4. 生产者、消费者各自按独立范围适配；中间状态不得被描述成整个系统已经可用。
5. 集成任务在组合层验证，记录采用的契约、实现及代价版本。

不要要求所有跨模块动作重新逐项批准：已授权的整体目标和范围应由集成任务推进。也不要把模块代理生成的 proposal 当作用户已授权的证明。

## 4. 必查的兼容性问题

- 老记录能否读取；不能读取时是否显式拒绝，而不是静默解释成新语义。
- 生产者和消费者是否使用同一版本、单位和状态定义。
- “未知”“不适用”“预算耗尽”“明确不支持”是否仍可区分。
- 预测与实测、逻辑大小与实际分配、局部合法与全局可行是否仍有清楚边界。
- 新实现或新代价是否追加版本，避免修改正在被计划使用的快照。
