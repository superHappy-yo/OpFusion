# 算子与设备扩展任务模板

该模板适用于已有公共契约内的插件扩展。任务只需写在对话或任务正文中。模板不扩大权限，实际范围以用户授权和仓库规则为准；当前仓库只有规格，真实实现和验证命令须在工具链建立后填写。

```text
任务：<新增或完善哪项能力>
扩展类别：<operators/devices/compilers/implementations>
plugin_id：<命名空间内稳定且唯一的 ID>
所属目录：extensions/<category>/<plugin_id>/

先读根 AGENTS.md、extensions/AGENTS.md、extensions/README.md、
modules/contracts/extensions.md 和目标插件已有说明。
只读依赖：<所需公共契约、provider 声明及版本>
允许修改：<目标插件内具体文件或子目录；排除全部治理提示词>
禁止修改：核心模块、apps、其他插件、公共契约、根依赖/构建/CI、
          所有 AGENTS.md/CLAUDE.md 及范围/所有权策略。

输入与输出：<包括 shape/dtype、属性、数值、状态或资源要求>
复用能力：<已有 provider ID、版本、接口及适用条件>
新增贡献：<语义/前端绑定/分解/参考方案/lowering/设备描述/执行适配等>
支持矩阵：<来源版本 × 算子条件 × 目标架构 × 软件版本；列出不支持范围>
公共契约影响：<无，或已获授权的集成任务及精确范围>

实现前解释：为何只增加本插件就能被发现和使用；哪些能力尚不可执行。
使用组合与小型接口，不在核心增加按算子名或设备型号判断的分支。
通过 plugin.toml 声明贡献，不编辑中央列表、不依靠库加载或静态初始化副作用注册。
不导入兄弟插件或核心模块具体实现；通过端口和版本化 provider 引用复用。
若契约不足，先在本插件 proposals 中说明最小修改，不创建影子类型绕过它。

验收条件：
- 新增/移除插件后发现结果正确，不修改核心文件即可接入。
- 重复 ID、绑定冲突、API 不兼容、缺失依赖得到确定诊断。
- 导入时没有设备初始化或测量等副作用。
- 新算子具有语义/shape 校验、fixture、参考结果与边界测试。
- 新设备分别证明描述可识别、provider 兼容和目标执行可验证。
- 未测成本为未知；仅发现、支持、编译、验证、实测状态不混淆。
- 实际 diff 和全部新文件均属于允许路径。

完成报告：贡献、修改路径、支持矩阵、真实验证命令及结果、
          未验证的设备/语义范围、需要协调的契约变更。
```

## 算子任务需要明确的差异

算子注册至少要表达稳定语义、shape/dtype 推导与校验、前端版本绑定、参考依据和可执行方案。可执行方案可以是自己的实现，也可以是在数值政策下可验证地分解为已有算子。首次缺少通用加载器时，应先通过集成任务建立加载器，不让第一个算子任务顺带修改全部核心模块。

下面是任务范围示例，表示未来目录，不宣称插件已经存在：

```text
任务：新增 Sigmoid 算子扩展。
所属目录：extensions/operators/org.example.sigmoid/
允许修改：该目录下 plugin.toml、src/、tests/、README.md、proposals/。
目标：绑定指定 ONNX opset 的 Sigmoid，校验形状和 dtype，提供参考与目标方案。
验收：给定支持子集内数值正确；非法类型拒绝；未知设备不虚报支持；
      frontend、fusion、codegen 等核心无改动。
```

## 设备任务需要先分类

| 任务类型 | 必须说明 |
|---|---|
| 已有架构的新型号 | 已有编译器/执行 provider 为什么支持该型号；新增识别信息、资源描述和验证范围 |
| 已有型号的新实例 | 运行时探测/配置如何产生实例身份、可用资源和软件环境；不为每台机器复制实现 |
| 新架构或 SDK | 哪些编译/加载/执行/同步接口必须新实现；哪些接口可复用；单插件或明确授权的多个插件范围 |

仅增加设备峰值参数不能通过“可执行”验收。没有实机条件时可以交付描述和适配规格，但要报告实际未验证的范围，不伪造性能数据。
