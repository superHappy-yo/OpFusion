# AI 独立审查提示词模板

默认审查任务只读，不同时修复被审查文件。用户明确要求“审查并修复”时，仍需先确定修复范围，并遵守同样的模块边界。

```text
任务：审查 <变更、分支或文件集合>。
审查模式：只读。
授权写入范围：无。
预期模块范围：<本次任务应涉及的路径>
相关契约/版本：<应遵守的公共定义>

先读根及相关模块 AGENTS.md、docs/ai/scopes.json、任务正文和实际 diff。
逐条检查范围、模块依赖、接口兼容、正确性和验证证据。
用具体文件位置、触发条件和最小反例说明问题；区分确认缺陷、合理简化、证据不足和建议。
不把缺少新测试本身当成缺陷，说明缺少哪项行为验证及其影响。
不修改文件，不新增依赖，不为了完成审查运行真实部署或破坏性操作。
如未发现阻断问题，明确报告剩余验证范围，不虚构风险或实验结果。
```

## 审查清单

| 方面 | 应检查的问题 |
|---|---|
| 修改范围 | 是否出现其他模块、治理提示词、公共契约、根配置的未授权变更？新增、删除和重命名是否纳入？ |
| 依赖方向 | 是否通过私有导入、循环调用或全局状态绕过公共端口？装配是否留在应用层？ |
| 契约一致性 | 字段、单位、版本、错误状态、所有权和生命周期是否一致？ |
| 图语义 | 是否保持操作数端口、唯一生产者、区域覆盖、外部输出和商图无环？ |
| 执行状态 | 是否区分逻辑张量、物理副本、缓冲分配与设备可访问性？ |
| 代价与资源 | 是否注明实现和环境条件？预测与测量是否分开？工作区是否重复计费？ |
| 反馈闭环 | 是否冻结本轮快照、新记录追加版本，并具有预算、停止和回退语义？ |
| 证据 | 测试是否实际执行？是否将模拟或单设备结果升级为分布式实测结论？ |

## 发现的输出格式

```text
严重程度：<阻断/重要/一般>
位置：<文件及行号或明确段落>
确认事实：<代码、规格或输出表明什么>
触发条件/反例：<何时会产生错误>
影响：<对接口、行为或验收的影响>
最小修改建议：<应由哪个模块在什么范围内处理>
证据限制：<尚未检查或无法验证的部分>
```

允许“未发现必须修复的问题”作为结论；不能为了凑条数把设计偏好写成错误。审查输出是建议和证据，不自行授予其他代理修改范围。
