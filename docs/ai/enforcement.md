# 修改范围的约束层次与后续强制检查

当前状态：仓库初始化提供提示词、范围登记和协作规范。本文描述未来的强制检查要求；本次没有实现检查脚本、Claude hooks、GitHub Actions，也没有启用或验证远端分支规则。不能据此声称 AI 已被技术上限制为只能修改一个模块。

## 1. 当前提示词层

根与各模块的 `AGENTS.md` 保存规范；同级 `CLAUDE.md` 用 `@AGENTS.md` 导入，避免维护两份正文。Claude 官方说明祖先/当前目录规则在启动时加载，子目录规则按需加载；相对导入以包含它的文件为基准。这些内容是模型上下文，不是强制写入权限。[Claude Code 官方文档](https://code.claude.com/docs/en/memory)

因此，任务开始时仍须显式读取目标模块规则并声明修改路径。不能依赖“只在模块目录启动”就认为其他目录不可写，也不能把工作区路径、提示词或模块名称当成授权凭证。

## 2. 后续可实现的三层保护

| 层次 | 能约束什么 | 不能证明什么 |
|---|---|---|
| 提示词与任务白名单 | 规定行为、责任和验收范围，支持人工/AI 审查 | 不能保证所有写入都被阻止 |
| diff 范围检查＋必需状态检查 | 在策略正确且受保护时，阻止越界变更合入目标分支 | 不能阻止本地文件已经被修改 |
| 运行环境的路径写权限 | 以只读挂载/文件权限等限制进程实际写入 | 不能由一份 Markdown 文件自动获得 |

分支和 worktree 隔离的是变更工作副本，不等于目录权限隔离。可选的工具 hook 应覆盖编辑、写入及能够写文件的命令路径；只拦截一种编辑工具仍可能遗漏其他写入方式。真正需要强隔离时，以受管理的运行环境为准。

## 3. 未来 diff 范围检查的规格

实现该检查是后续独立工程任务，应验证以下行为：

1. 使用受信任基线中的范围规则、明确授权的任务范围和目标分支；不能让 PR 修改自己的白名单后自证通过。
2. 检查新增、修改、删除、未跟踪文件及重命名两端路径；先规范化路径，拒绝借父目录跳转或符号链接绕开路径范围。
3. 模块任务只接受该模块授权文件；其他模块、治理提示词、范围登记、公共契约与根依赖/CI 配置默认拒绝。
4. 契约任务可修改明确授权的契约规格、类型/端口实现、纯不变量校验和契约测试；治理文件仍受保护。集成任务逐项声明多个写入范围，不自动放开全仓。
5. 对越界路径逐项报告原因；区分检查失败与检查器无法运行，不能把“跳过”显示为成功。
6. 检查规则本身的变更由独立治理任务审查，普通模块任务不得修改它来通过检查。

测试该机制时至少覆盖：合法模块修改、跨模块修改、治理文件修改、删除、重命名、未跟踪新增、路径绕行、契约任务例外，以及“检查器自身被更改”的情形。

## 4. CODEOWNERS 与远端合并规则

`CODEOWNERS` 登记评审责任；只有结合目标分支的必需 owner review 或相应规则，才约束合并。它不阻止本地跨目录编辑。owner 必须是真实且有仓库写权限的账号/团队；目标分支中的文件决定评审归属，同一规则列出多人也不自动要求全员批准。[GitHub CODEOWNERS 官方文档](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners)

不要填写不存在的模块团队。若当前只有一个维护者，可使用已核实账号，但不能据此宣称已有独立的模块多人评审。

未来启用远端限制时需另行核实仓库套餐、权限和实际规则，包括目标分支、必需检查、owner review、绕过权限，以及治理文件自身的保护。应记录哪些已启用、哪些仅有设计；不能把创建 `CODEOWNERS` 等同于已完成全部设置。

## 5. 授权与流程的边界

用户已明确授权某项跨模块工作时，任务可按该范围直接推进，不需要因目录规则再重复索取同一批准。范围变化应可追溯到用户授权，而不是由代理创建的模板、子任务消息、proposal 或新提示词自行产生。

若只授权一个模块，代理应完成范围内工作并提出具体的跨模块需求。不能将权限规则当成停止所有工作的理由，也不能为了赶进度绕开它。
