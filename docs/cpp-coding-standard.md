# OpFusion C++ 编程规范

本文是供开发者和 AI 执行的项目规范，详细规则统一维护于此，根 `AGENTS.md` 只保留阅读入口。文中的“必须/禁止”是约束，“优先/建议”允许有明确理由的局部例外；例外应说明原因、影响和验证方式，不能通过修改规范为当前任务自行放宽边界。

## 1. 适用范围与项目基线

本规范基于仓库现有 [README](../README.md)、[依赖规则](architecture/dependency-rules.md) 和 [公共契约](../modules/contracts/README.md) 制定。当前仓库为规格与 AI 协作骨架，尚无 C++ 业务源码、构建系统、业务测试、`.clang-format`、`.clang-tidy` 或 CI 门禁。本文不是这些设施已存在或已验证的证明。

- 项目算法、领域模型、规划、代码生成协调与运行时等生产系统逻辑使用 C++；Python 仅用于测试。该语言选择是当前目标，不表示已有 C++ 实现或构建。
- Python 测试代码也应保持明确类型、单一职责和真实注释；不得承载生产算法、在线调优或生产正确性参考实现，也不得通过嵌入解释器/子进程把生产逻辑转回 Python。
- 首次实现 C++ 前，必须在对应任务中确定语言标准、编译器及版本、目标平台、异常/RTTI 策略、ABI 与构建入口。未确定前，不擅自假定 C++20/23 或引入相应库特性。
- 用户当前任务与运行环境约束优先；公共语义以 `modules/contracts/` 为准。本规范不能覆盖契约、扩大写入权限或改变模块依赖。
- 下文 C++ 示例均为**设计示意，不是仓库已有 API，也不是已编译示例**。示例中的类型需按真实实现任务落地，不应直接复制成新公共契约。

## 2. 类型建模：封闭状态用枚举，开放标识保持可扩展

### 2.1 必须优先使用 `enum class` 的场景

有限、明确、由本项目控制的类别或状态，应使用独立的强类型枚举，禁止在内部业务逻辑中用魔法字符串或整数分支。例如：

- 张量来源：`input / parameter / operator_result`。
- 能力结果：`supported / unsupported / unknown`。
- 候选验证状态：`pending / verified / failed`。
- 搜索结果：`found / budget_exhausted / not_searched`。
- 成本来源：`analytical / predicted / measured`。

这些是不同语义维度，必须分别建模，不能合并成一个万能 `Status`，也不能用一个 `ready` 布尔值代替。尤其不能把“编译成功”“可执行性验证通过”和“有实测时延”视为同一状态。

```cpp
// 设计示意：独立枚举表达独立语义，不代表已实现的契约映射。
enum class SupportResult { Supported, Unsupported, Unknown };
enum class ExecutionStatus { Pending, Verified, Failed };
enum class CostSource { Analytical, Predicted, Measured };
```

- 新枚举使用 `enum class`，不引入未限定作用域的普通 `enum`。
- 处理封闭枚举时显式覆盖全部有效分支；不得用返回成功的 `default` 掩盖新增枚举值。反序列化入口仍必须拒绝或明确处理无效整数，不能假定强制转换后天然合法。
- 只有协议、ABI 或位操作确有要求时指定底层类型与数值；枚举序号不是天然稳定的外部协议。
- 真正二选一的事实可以用 `bool`，例如是否启用诊断。多状态、可未知状态或带有策略含义的选项使用枚举/可选值，不堆叠多个布尔参数。

### 2.2 字符串允许存在的边界

字符串适用于名称、路径、日志、诊断、用户输入、源模型字段与可扩展 ID；“不用字符串”指不使用字符串替代本可静态表达的内部类型，不是禁止所有字符串。

1. 在 CLI、配置、模型导入或序列化边界，将外部文本解析为内部强类型。
2. 解析时校验合法值、大小写政策、版本与缺失值；非法输入返回带字段和原值上下文的结构化错误。
3. 输出通过集中定义的格式化/序列化映射转回稳定文本。不要在各模块重复维护字符串表。
4. 未知外部值不能静默变成第一个枚举、成功、CPU 或“支持”。若协议允许保留未知值，必须使用显式未知状态并保存必要原值；否则明确拒绝。
5. 不能为避开枚举维护，把核心字段塞入 `map<string, string>` 或任意键值袋。

### 2.3 开放扩展不是封闭枚举

OpFusion 的算子、设备型号、编译器与实现提供者是开放集合，身份必须遵守 [扩展契约](../modules/contracts/extensions.md)。**禁止创建需要每次新增插件都修改的中央 `OperatorKind`、`DeviceModel` 或提供者枚举。**

- `OperatorKey` 保持 `namespace + name + semantic_version` 的身份语义；`plugin_id`、提供者 ID 等可用受校验的强类型字符串封装。
- `TensorId`、`NodeId`、`RegionId`、`DeviceId` 等不同身份不得仅以同一种裸整数/字符串互换。优先采用小型值类型或既有强 ID 设施；`using NodeId = string` 这类别名本身不提供类型隔离。
- 不为每一种 ID 引入复杂框架；统一比较、哈希与序列化即可。跨语言/持久化表示遵守契约，不私自改变 wire 格式。
- 核心查询语义、traits、能力与提供者端口；不以 `if (op_name == "Conv2D")` 或设备型号字符串决定通用调度与支持性。
- `dtype`、布局、trait 等是否为封闭集合，应由对应契约决定，不能只因当前示例很少就封死扩展。

## 3. 对象与类：一个概念一份模型，一个类一项明确职责

### 3.1 如何理解“每个对象一个类”

一个具有独立职责、状态或不变量的**领域概念**应有清晰类型，而不是为每个实例创建一个类，也不是为每个名词创建继承层级。

- 同一种节点的多个实例使用同一类型和不同 ID，不生成 `Node1`、`Node2` 等类。
- 纯数据记录优先 `struct`/值类型；维护资源、状态机或必须控制的不变量时使用封装良好的 `class`。
- 不为了面向对象而给无状态纯计算套一层只有静态方法的类；内部自由函数或小函数对象通常更简单。
- 不把语义算子、设备、实现、代价和执行缓冲合并为“万能对象”。分别对应契约中的身份和生命周期。

### 3.2 类的责任与文件组织

- 一个类必须能用一句话说明主要责任；接口中出现导入模型、搜索划分、调用编译器、启动设备、写报告等多个阶段时，应拆分。
- `GraphSpec`、`RegionSpec`、`CostRecord` 等记录不能因为方便就持有硬件句柄、RPC 客户端或其他模块的可变内部对象。
- 公共头文件原则上以一个主要公开类/概念为中心，文件名反映该概念。紧密关联的小型枚举、结果记录、traits 或私有辅助类型可以同文件；不机械规定每个小类型必须一个文件。
- 实现细节放 `.cpp` 或明确的私有头文件，不将所有实现堆到一个头文件。模板和必要内联按真实工具链需要处理。
- 不创建万能 `Manager`、`Context`、`Utils` 类作为无边界容器。命名应能说明领域职责，如区域边界分析、候选代价预测，而不是泛指“处理”。

### 3.3 组合、端口与继承

- 优先组合与显式依赖注入；跨模块依赖使用 contracts 定义的小端口。
- 只有存在真实可替换行为和调用边界时引入虚接口；不要求所有具体类都有接口，也不为未来可能的扩展预建空实现。
- 禁止万能 `Operator`/`Device` 基类和深继承树。设备描述与编译/执行能力分开，不要求一个设备类实现全部工具链。
- 多态基类若允许通过基类指针销毁，析构必须满足相应安全要求；明确对象所有权，不通过继承掩盖生命周期。
- `apps` 负责装配，业务类不得自行查找全局 registry、加载邻居实现或初始化设备。

## 4. 模块边界与数据契约

C++ 的 `#include`、链接依赖、工厂和回调同样受 [依赖规则](architecture/dependency-rules.md) 约束，不能因语言不同绕开所有权。

- `contracts` 只定义领域数据、公开端口与不变量，不依赖业务模块、硬件 SDK、模型框架、RPC 或数据库。
- `frontend/backends/cost_model/fusion/planner/codegen/runtime` 只依赖自身实现与 contracts 的公开接口；其他能力由 `apps` 注入。
- `extensions` 只使用自身代码、contracts 与声明的第三方依赖；不导入兄弟扩展或核心内部代码。
- `experiments` 通过 contracts 和 apps 的公开实验入口工作；生产模块不依赖 experiments。
- 图级融合、分布式规划与区域内部代码生成保持既有责任边界；不要为了减少类数量把三个阶段合为单个优化器。
- 已发布的图、候选、成本与快照使用不可变值语义；更新形成新记录/版本，不原地改变旧计划引用的内容。
- 单一事实来源明确。图边表是输入输出关系的派生视图；不得多处维护可相互矛盾的 producer/consumer 真值。
- 单位进入字段名或单位类型，例如 `latency_us`、`workspace_bytes`；逻辑大小不等于流量，逻辑张量不等于物理缓冲。

## 5. 资源、所有权与生命周期

- 优先作用域对象与值语义。内存、文件、锁、编译模块和设备资源使用 RAII；原始 C/SDK 句柄只在适配边界封装。
- 需要独占动态所有权时优先 `std::unique_ptr`；仅在真实共享所有权且生命周期可解释时使用 `std::shared_ptr`。避免环状共享持有。
- 裸指针和引用默认借用、不拥有；可空性、借用期限和是否跨异步调用必须明确。不得仅凭 `const` 推断线程安全或深度不可变。
- 检查容器扩容、移动、缓存淘汰对指针、引用、迭代器、`string_view` 和 `span` 的影响；后两者仅在已选语言/库标准支持时使用。
- 设备异步执行的资源必须活到使用完成，不能把 host 函数返回当作 GPU 已完成。输出缓冲、工作区与传输副本按执行契约释放。
- 优先 Rule of Zero。自己管理资源时显式审查析构、复制、移动以及失败路径；禁止仅靠正常路径手工释放。
- 析构不传播异常；需要报告释放失败的资源提供显式关闭/完成接口，并采用项目统一诊断机制。

## 6. 函数、配置与错误处理

- 函数只完成一项可描述的工作；复杂流程按语义阶段提取函数，不用任意行数阈值强拆。
- 使用类型化配置记录，不传递含义不明的字符串策略或连续布尔参数。配置在入口校验一次，内部依赖已明确的前置条件。
- 小型标量按值传递，大型只读对象按适当的 const 借用传递；需要保存参数时明确复制或所有权转移，避免长期保存临时对象引用。
- 不使用输出参数模拟本可清楚返回的结果；多个关联输出使用具名结果类型，不返回含义不明的长 tuple。
- 错误处理遵守首次 C++ 集成确定的异常/结果类型策略，不混用互不兼容的机制。没有既有 `Result<T>` 时，不冒称它已存在或私自新增公共实现。
- 失败必须区分非法输入、不支持、未知、预算耗尽、编译失败、验证失败等语义；附请求/对象 ID、阶段和可操作原因。
- 不忽略 SDK 返回值，不吞异常，不返回空结果冒充成功，不用 `assert` 代替外部数据校验。
- 可选值表达“尚未取得”，不能用 `0`、空字符串或负数偷偷表示未知。已知零成本与未知成本必须可区分。
- 禁止未初始化状态、隐式窄化与无依据的强制转换。尺寸乘法、字节计算、索引与有符号/无符号混用需检查溢出和范围。
- `const`、`explicit`、`override` 按语义使用；`noexcept` 必须有真实保证，不为消除告警机械添加。

## 7. 命名、排版与头文件

仓库尚无 C++ 历史实现可供继承。以下为新增 C++ 的默认约定；以后某模块存在已明确批准的不同风格时，局部保持一致，不借规范任务批量改名。

| 对象 | 默认约定 | 示例（设计示意） |
|---|---|---|
| 类型、类、结构体、枚举 | `PascalCase` | `RegionBoundary`、`CostSource` |
| 函数、方法、变量、数据记录字段 | `snake_case` | `validate_region`、`latency_us` |
| 私有成员 | `snake_case_` | `registry_snapshot_` |
| 常量 | `kPascalCase` | `kDefaultCandidateLimit` |
| 枚举项 | `PascalCase` | `SupportResult::Unknown` |
| 命名空间 | 小写，按归属分层 | `opfusion::contracts` |
| C++ 文件 | `snake_case.h` / `.cpp` | `region_boundary.h` |

- 公共契约字段名保持既有语义与序列化名称；代码命名不能隐式改变外部协议。
- 避免 `data`、`info`、`temp`、`flag` 等缺乏上下文的名称；短循环索引在局部清楚时可用。
- 沿用 `.editorconfig`：UTF-8、LF、空格缩进、文件末尾换行、无行尾空格；C++ 当前默认两空格。
- 控制语句使用大括号，即使只有一条语句。避免一行多个语句或嵌套条件表达式掩盖控制流。
- 直接包含实际使用的头文件，不依赖传递包含；公共头文件自包含，使用一致的 include guard。
- 公共头文件禁止 `using namespace`；不向 `std` 添加未获标准许可的声明。
- `.cpp` 内部辅助符号限制可见性，避免不必要的公共导出与宏。常量优先语言内建的常量机制，而非预处理宏。
- 新增 `.clang-format` / `.clang-tidy` 属于独立配置变更，需在任务范围内明确授权并匹配固定工具版本；本文不假定它们已部署。

## 8. 注释规范：记录契约、理由和不变量

### 8.1 需要文档注释的内容

公开类型、跨模块接口、非显然的资源/数值/并发行为使用统一的 Doxygen 风格 `///` 或 `/** ... */`。新文件默认 `///`；已有文件保持一种风格，不混排。

- 类：主要职责、关键不变量、所有权与线程安全条件；说明不负责的边界仅在容易混淆时需要。
- 函数：语义、必要前置条件、返回结果及失败语义；涉及借用、异步、单位、预算、数值容差时必须写明。
- 字段：无法从名字判断的单位、有效范围、来源或未知值含义。不要给每个显然字段重复写“这是某字段”。
- `@param`、`@return`、`@throws` 按实际需要使用，不能为了填模板写空话；无异常接口不要添加虚假的 `@throws`。

```cpp
// 设计示意：类型名仅用于展示注释结构，不是已实现接口。
/// 计算区域必须保留的外部输出，不修改语义图。
/// @param graph 借用的、已验证的不可变图；仅在调用期间使用。
/// @param region 属于 graph 且成员非空的区域。
/// @return 被区域外消费者使用或属于模型输出的区域内张量 ID。
/// 同一张量只出现一次；顺序由实现明确规定并保持稳定。
/// 不分配设备缓冲，也不推断区域已经可执行。
std::vector<TensorId> collect_boundary_outputs(
  const GraphSpec& graph, const RegionSpec& region);
```

### 8.2 算法与实现注释

注释解释“为什么必须这样做”，以及仅从代码不易看出的约束。例如：

```cpp
// 设计示意：外部分支仍读取 Conv 输出，因此融合区域必须保留该边界值。
// 不能因为 ReLU 已在区域内计算，就把所有中间输出从接口中删除。
```

值得注释的内容包括：商图无环条件、归约完整后才能进行非线性后处理、剪枝下界的适用条件、缓存键所覆盖的版本、锁顺序、异步资源存活期、浮点重排限制和预算归属。

禁止以下做法：

- 逐行翻译代码，例如 `++count; // 将 count 加一`。
- 用注释宣称代码尚未保证的“线程安全”“零开销”“最优”“所有输入正确”。
- 用大段注释代码保存旧实现；历史由版本控制保存。
- 注释与代码语义不一致却只修改代码；接口变化时同步更新注释和对应契约说明。
- 在代码注释中加入聊天记录、AI 操作叙事、个人信息或无关论文全文。

注释默认使用清晰中文，保留标准 API/术语英文；对外英文接口或既有英文文件保持一致，不无理由翻译全文件。公开文档与注释不得包含本机绝对路径、凭据或不可分享数据。

### 8.3 TODO 与临时处理

`TODO`/`FIXME` 必须包含具体问题、原因及删除/完成条件，能关联 issue 或设计记录时附相对链接/编号。没有 issue 时记录明确触发条件，不伪造编号或负责人。临时绕过不能代替错误处理，也不能仅凭 TODO 获得跨模块修改权限。

## 9. 性能、并发与设备边界

- 先保证语义、接口与错误路径正确；避免明显的重复解析、热点分配和不必要复制，但性能提升必须由同口径证据支持。
- 成本估计必须关联完整候选、设备/实现条件与来源。不能把“少一次张量写回”直接注释为“更快”。
- 不因优化而改变浮点精度、归约顺序、别名政策或输出就绪时机；需要变更时走数值/接口契约流程。
- 明确共享对象的可变性、锁责任和调用线程；不要把 `std::shared_ptr` 当成数据同步机制。
- 锁使用 RAII，记录必要锁顺序；持锁调用外部端口/回调必须检查重入和死锁风险。
- runtime 事件绑定 run、attempt 与 plan 版本；旧事件不能完成新任务。超时不等于远端已停止，释放与重试需要显式生命周期依据。
- 设备句柄与框架对象留在后端/运行适配层。同步、设备探测、编译、RPC 不得隐藏在纯规划、属性访问器或普通构造中。

## 10. AI 修改与验收清单

开始前：阅读根与目标目录规则，声明 owner module、允许路径、契约版本和基线。不得以“统一规范”为由重构无关代码、修改公共契约或新建全仓工具链。

完成前逐项检查：

- [ ] 封闭状态使用强类型；开放扩展没有被中央枚举或名称分支封死。
- [ ] ID、单位、未知值与失败原因不会混淆；边界解析有校验。
- [ ] 每个类型有清晰职责，数据/行为/资源分离，没有机械类包装或深继承。
- [ ] 依赖方向、公共契约、不可变快照与异步生命周期保持正确。
- [ ] 注释描述真实契约和非显然理由，示例/规划/实测明确区分。
- [ ] 没有新增无关路径、依赖、批量格式化或告警抑制。
- [ ] 对新增行为提出相应边界与失败测试；修复缺陷时提供可暴露原问题的回归用例设计。
- [ ] 报告真实做过的检查，以及未编译、未测试、无硬件等限制。

**执行约束：未获用户明确要求，不在本机执行编译或测试。** 可以进行任务允许的只读检查和文档一致性检查，列出待执行验证计划；不得因为本规范提及测试就自行运行构建。当前仓库无测试命令，不虚构命令或声称通过。后续在获准环境中验证时，使用实际登记的工具链和命令。

`clang-format` 负责排版，`clang-tidy` 仅覆盖部分静态规则；它们不能证明语义、并发、数值和性能正确。不得通过删除测试、放宽数值容差、大范围 `NOLINT` 或关闭检查掩盖问题。

## 11. 参考与规则来源

本文件是 OpFusion 的项目规则，不是以下指南原文，也不要求同时无条件遵守多个指南。项目语言、错误处理和扩展政策以本仓库决定为准。

- [ClangFormat Style Options](https://clang.llvm.org/docs/ClangFormatStyleOptions.html)、[Clang-Tidy](https://clang.llvm.org/extra/clang-tidy/)：未来工具配置参考，必须与实际固定版本匹配。
