# 架构决策记录

状态说明：`采用` 表示当前设计约束已选定，不表示相关代码已经实现；`待决` 表示在明确触发条件出现前不预先选型。本文件不记录未经测量的性能保证。

## ADR-001：模块化单仓库与两个运行角色

状态：采用。

背景：三个研究内容需要共享语义、候选、代价和执行记录；算法之间又必须有清楚边界。现在没有证据支持把每个研究模块独立部署。

决策：建立九个模块，apps 为唯一装配入口。部署侧区分协调端与工作端；runtime 内保留 coordinator、worker、transport、artifact store 职责，不立即拆成多个服务。

结果：支持先在本地完成可执行闭环，再沿明确的 worker 协议扩展至多设备和跨主机。不能把逻辑模块数量等同于进程或服务数量。

重新评估条件：真实并发、故障隔离或团队部署需求证明需要独立服务；评估须包含运维和协议成本。

## ADR-002：Ports and Adapters 与显式依赖注入

状态：采用。

决策：contracts 定义纯 DTO 和 ports。frontend、backends、cost_model、fusion、planner、codegen、runtime 只导入 contracts 的公开 API，不互相导入具体实现。apps 创建并注入端口实现。experiments 可使用 apps 公开运行入口，业务模块不依赖 experiments。

结果：设备库、预测器和存储实现可以替换，算法单元测试能够使用受控替身。端口不应为了每个函数建立抽象，只在跨模块、硬件或 I/O 边界使用。

禁止事项：全局可变 Service Locator、模块间隐式注册、导入时硬件探测，以及通过动态导入绕过依赖规则。

## ADR-003：不可变记录与版本快照

状态：采用。

决策：语义图、区域接口、实现候选、成本、产物清单和执行计划都具有稳定标识及明确版本。单轮规划读取冻结快照，新增测量或实现产生新记录，由 apps 决定是否发布下一快照。

结果：可追溯计划使用的精确实现和成本，也能失败回退。预测与实测不得覆盖彼此；同一接口的新实现仍需重新检查时序、容量和组合正确性。

限制：版本化不等于采用事件溯源系统或分布式共识。早期可使用普通文件和清单，保持相同领域语义即可。

## ADR-004：策略可替换，默认实现明确

状态：采用。

决策：成本预测、融合候选保留、调度和区域内部搜索可以各自提供可替换 Strategy。每个阶段先有范围清楚的基线策略，通过显式配置和 registry 选择；具体策略由 apps 装配。

结果：算法比较能够固定候选、接口、设备与预算。不允许默认策略悄悄调用额外调优、扩大候选空间或使用测试标签。

限制：当前不建设自动发现任意第三方插件的平台。引入新策略应先证明与现有端口一致，并记录其独立预算与适用条件。

## ADR-005：显式执行状态机与尝试标识

状态：采用原则，具体消息协议待实现前定稿。

决策：任务执行必须有明确状态迁移、run/task/attempt 标识，以及取消、超时、失败和重复请求的含义。运行时按固定计划执行，实际环境不匹配时返回失败或拒绝状态，由 apps 决定重规划。

结果：避免将网络重试误当作重新执行授权，避免 worker 自行改变计划。原始事件需要关联对应尝试和计划版本。

限制：不承诺网络层“恰好一次”。允许哪些幂等重试、何时能够安全回收资源，应在相应执行和传输契约中明确验证。

## ADR-006：Python 控制面与成熟后端适配

状态：采用初始方向。

决策：算法和控制面默认使用 Python；模型规范化后的数据通过 contracts 交互。计算使用成熟库/编译后端，native 代码仅在必要的设备接口或经测量确认的热点中引入。

结果：首版优先验证语义、接口和系统闭环，而不是同时重写编译器、内核库和通信栈。后端依赖限制在 backends 或 runtime 的具体适配层，不能渗入 contracts。

重新评估条件：真实开销或外部后端要求说明语言边界需要调整。调整必须保留契约版本和测量证据，不以“可能更快”为理由整体重写。

## ADR-007：硬件定义与探测实现分离

状态：采用。

决策：设备、引擎、内存池、链路及能力记录的类型由 contracts 定义；实际探测、软件支持判断、默认程序、编译和设备执行由 backends 提供。不建立单独 platform 模块。

结果：硬件类别、软件后端和具体实现不混为一谈。CPU/GPU/NPU 标签本身不能证明某区域可执行；资源字段区分未知、不适用和实际为零。

限制：统一接口不要求统一性能公式，也不意味着新增设备无需后端、数据和验证。

## ADR-008：完整张量边界与保守资源核算

状态：采用首版约束。

决策：区域之间按完整张量就绪执行；区域内部可采用 tile 复用。跨区域逻辑值不可变，不允许未声明的输入输出别名。调用方输出缓冲在区域开始前分配；工作区按内存池覆盖执行区间保守保留。

结果：简化事件和缓冲正确性验证。首版可保守串行同设备计算；启用复制重叠必须有明确的硬件和资源依据。

限制：该选择可能拒绝实际可行的细粒度重叠，不能声称最优并发或精确内部内存轨迹。引入提前输出、跨区域流式执行或原地覆盖时，需要新的契约和验证，不得只改调度器。

## ADR-009：跨主机 RPC 与数据传输库

状态：待决。

触发条件：第一个需要真实跨主机执行的纵向用例开始实现之前。

需要决定：控制消息编码和版本兼容、RPC 库、张量数据通路、超时、重复消息、取消、产物分发、缓冲所有权和鉴权边界。选择应基于目标平台、依赖成本和可验证的最小用例。

当前约束：不提前声称支持 gRPC、MPI、RDMA、NCCL 或任意其他具体协议；也不将模拟执行或单机多后端称为跨主机系统。

## ADR-010：提示词边界与可执行门禁分别处理

状态：采用原则；强制检查实现待代码阶段。

决策：根及模块提示词定义默认修改范围、契约所有权和验收方式。模块任务不能通过修改提示词自行扩权。明确授权的跨模块任务按范围执行，并记录消费者影响和验证。

结果：AI 接到任务后应先定位所有权，使用公开接口，完成后核对 diff；发生契约缺口时提交具体变更范围而不是复制实现。

限制：提示词不是文件系统或仓库权限。实际的路径检查、导入边界检查、CODEOWNERS 和分支规则只有实现、配置并验证后才构成门禁，当前不能宣称已经强制生效。

## ADR-011：当前初始化不引入的复杂机制

状态：采用。

本次不增加微服务网格、Kubernetes 部署、全局事件总线、自动插件发现、分布式共识、复杂 ORM、事件溯源框架或全局 `utils` 模块。也不为了目录完整性预生成尚无需求的框架代码。

每项新增基础设施必须由具体用例、瓶颈或故障要求驱动，并说明现有简单方案为何不足。架构可扩展性来自清楚的契约和所有权，不来自预先堆叠抽象层。
