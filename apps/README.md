# apps — 应用装配与优化流程

状态：规格目录，尚无 CLI 或服务入口。这里是唯一 composition root。

输入是用户模型/任务、平台和部署配置、全局优化预算。输出是选定计划、执行结果及完整来源记录。apps 选择并注入 frontend、预测器、候选策略、planner、codegen、backend、runtime 和存储端口；不在入口内重写这些算法。

## 预定流程

1. 按扩展契约发现 manifest、解析依赖并冻结 registry；实例化所需提供者，显式探测设备。接收 ModelPackage、OptimizationRequest 与 DeploymentContext，导入图与数值政策。
2. 构建默认参考实现；记录能力未知与验证失败，不能假定所有平台都支持。
3. 通过 fusion 和成本/能力端口产生候选快照 e。
4. planner 结合部署环境产生固定 ExecutionPlan；runtime 执行并产生原始记录。
5. 按预算构建固定区域/设备/接口的 TuningRequest，交 codegen 优化。也可在正式计划形成前对保留的探索区域请求生成；必需语义 oracle，可选 seed_candidate，不要求先有 planner 选中的实现。
6. 新结果写入新记录和快照 e+1；重新验证计划、容量、数值与端到端效果，通过则接纳，否则保留已有可行计划。
7. 预算或轮数耗尽停止；未找到可行计划与已证明不可行必须区分。

未来入口可以包含本地运行、Coordinator、Worker 和实验命令。它们属于两个运行角色与少量 CLI，不代表要部署每个算法模块为独立服务。RPC/配置格式在对应 ADR 和工具链任务中确定。

## 验收

- 只从配置/参数显式装配依赖；不靠导入副作用或全局 Service Locator。
- 一轮规划只使用一个候选快照；新后端、预测器或策略可替换而不用改调用方内部。
- 研究一、二、三以及编译/测量总预算分别可追溯。
- 固定 Conv 图先跑完整默认链路，再逐项替换优化器；不要一次引入所有优化后无法归因。
- 发现器是统一框架，只枚举约定插件目录、验证 manifest 和解析工厂；新增插件不修改这里的 import 列表或中央白名单。设备探测、编译、运行分别显式执行。
- 普通插件内容归 extensions。apps 不将插件适配逻辑搬进装配层；发布的图、profile、候选和计划必须绑定一致的 registry 及版本。

所有集成测试和示例可按需放在 `apps/tests/`、`apps/docs/`。它们仍受明确任务范围约束；本目录所有权不自动授权编辑所有被调用模块。
